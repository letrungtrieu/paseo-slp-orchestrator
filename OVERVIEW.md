SLP Orchestrator runs a Lead-designed multi-agent software delivery pipeline inside Paseo. You describe a feature to a Supervisor agent in chat; the Lead defines stages, goals and peer assignments as JSON, and the finished pipeline waits for your approval before its worktree is integrated into your base branch.

How it works: every agent receives a private MCP tool bus hosted by the plugin and can only call the tools of its assignment. The Lead creates a worktree, defines any number of ordered stages, and may place multiple peers in one stage. Peers share the stage goal, work concurrently, exchange direct messages and submit reports; the Forked Lead approves or reworks the stage. Completed stage peers are archived and fresh peers receive the previous result for the next stage. Pipeline state, reports, direct messages and the audit trail live in `~/.slp-orchestrator/orchestrator.sqlite3`, outside your repositories.

Setup: plugins must be enabled on the daemon, Paseo 0.11.4 or newer, Linux or macOS, a Node.js 24+ daemon runtime with built-in SQLite, and `git` on the PATH. Run state is kept in `~/.slp-orchestrator`. The plugin serves its tool bus on a loopback port only. The Forked Lead uses a native Claude session fork, so the lead provider should be Claude; other providers rebuild context through the SQLite-backed read tools.

Operating modes: new installations default to full auto. Forked Lead approval remains part of every stage; step-by-step debug adds a human gate after each stage, while semi-auto adds a human gate before integration. Mode, per-role model, thinking and permission selections save automatically in Paseo's host-wide plugin settings. Edit them from Start run or Settings → SLP Orchestrator; all clients connected to that host share the defaults. The Monitor panel shows every inter-agent call and the run detail shows each dynamic stage and peer.

Write boundaries: peers share the assigned pipeline worktree. Supervisor and Forked Leads receive read-only instructions and permission-hook rules. These are application-level controls; pipeline worktrees are visible in the Paseo sidebar.

Pipeline tools: `slp_create_worktree` and `slp_define_pipeline` create the Lead's ordered stages. Agents consult each other with the blocking `slp_ask` / `slp_answer` pair (questions and answers are stored in SQLite for auditing) or send one-way `slp_notify` updates, and Peers use `slp_stage_report` for evidence; the Forked Lead uses `slp_approve_stage` or `slp_stage_rework`. `slp_finalize_pipeline` and `slp_resume_pipeline` complete or continue the pipeline. Read tools return context immediately and do not end an agent turn.

Storage migration: the first load imports the old `state.json`, available Master Spec and acceptance documents, and repository communication logs in a single transaction. The old files remain as backups. Subsequent loads use SQLite and do not replay the import. New runs create no runtime task documents or logs in the repository. Old task-engine runs remain visible as read-only history and are not automatically resumed; start a new run to use the dynamic pipeline protocol. Existing agent sessions retain their original prompt/tool configuration. `SLP_HOME` can override the database directory.

Project workflows: selecting a repository prepares editable `.slp/SUPERVISOR.md`, `.slp/LEAD.md`, `.slp/QA_LEAD.md` and `.slp/peers/*.md` defaults while preserving custom prompts. YAML front matter defines each role's summary metadata (`role`, `name`, `description`) plus optional model/thinking overrides; unset choices inherit the SLP form. Summary metadata for all `.slp/peers` roles is injected into the Lead's `systemPrompt` so the Lead coordinates stages on its own, while each spawned stage peer receives the full agent prompt from its `.slp/peers/*.md` file. See [project workflow configuration](docs/project-workflows.md) for the pipeline JSON, stage lifecycle and snapshot behavior.
