SLP Orchestrator runs a multi-agent software delivery pipeline inside Paseo. You describe a feature to a Supervisor agent in chat; a Master Lead splits it into work packages, each package is built and reviewed by Peer agents in its own git worktree, and the finished result waits for your approval before it is merged into your base branch.

How it works: every agent receives a private MCP tool bus hosted by the plugin and can only call the tools of its role. The plugin routes all messages, checks each stage's git diff against the allowed file scope, runs the QA and Security fix loop (up to three rejected rounds before it pauses the task), and stores tasks, acceptance reports and the audit trail in `~/.slp-orchestrator/orchestrator.sqlite3`, outside your repositories. Before coding starts, a temporary Forked Lead, a copy of the Master Lead's session, reviews the Implementer's plan.

Setup: plugins must be enabled on the daemon, Paseo 0.11.4 or newer, Linux or macOS, a Node.js 24+ daemon runtime with built-in SQLite, and `git` on the PATH. Run state is kept in `~/.slp-orchestrator`. The plugin serves its tool bus on a loopback port only. The Forked Lead uses a native Claude session fork, so the lead provider should be Claude; other providers rebuild context through the SQLite-backed read tools.

Operating modes: new installations default to full auto, which only asks for final approval. Step-by-step debug pauses at every hand-over; semi-auto pauses at circuit breakers and before merging. Mode, per-role model, thinking and permission selections save automatically in Paseo's host-wide plugin settings. Edit them from Start run or Settings → SLP Orchestrator; all clients connected to that host share the defaults. The Monitor panel shows every inter-agent call and each work package appears as a progress card in the Supervisor chat.

Limits: write restrictions are enforced by prompts, a permission hook and a post-stage git diff check, not by an operating system sandbox. Task worktrees are visible in the sidebar on Paseo 0.11.4.

Task tools: `slp_define_tasks` stores the complete `masterSpec` text and task definitions together. Agents read context through `slp_get_run`, `slp_list_tasks`, and `slp_get_task`. `slp_stage_done` stores the implementation summary, `slp_verdict` stores review results, and `slp_doc_done` submits a structured acceptance report (`summary`, `changedFiles`, `technicalDecisions`, `qaResults`, `securityReview`, `risks`). `slp_get_report` retrieves task or project reports; `slp_report` and `slp_present_to_manager` persist the Lead and Supervisor assessments. Read tools return context immediately and do not end an agent turn.

Storage migration: the first load imports the old `state.json`, available Master Spec and acceptance documents, and repository communication logs in a single transaction. The old files remain as backups. Subsequent loads use SQLite and do not replay the import. New runs create no runtime task documents or logs in the repository. Existing agent sessions retain their original prompt/tool configuration; start a new run to use the new protocol throughout. `SLP_HOME` can override the database directory.

Project workflows: selecting a repository prepares editable `.slp/SUPERVISOR.md`, `.slp/LEAD.md` and `.slp/peers/*.md` defaults without overwriting existing prompts. YAML front matter defines role expertise plus optional model/thinking overrides; unset choices inherit the SLP form. The Lead receives metadata and chooses assignments without a required role kind, while each peer receives its own Markdown workflow. See [project workflow configuration](docs/project-workflows.md) for examples, extra peer spawning and snapshot behavior.
